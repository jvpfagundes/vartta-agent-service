# Debounce de mensagens fragmentadas e resposta em múltiplas mensagens no webhook do WhatsApp (v2)

A segunda passagem verifica as 11 correções da v1 (reserva de posição, limites, teto de espera, shutdown com timeout, `record_delivered_replies`, parser tolerante, cauda do agregado). Todas foram lidas no código e a suíte passa (79 testes); a reserva de posição não introduziu deadlock, perda de fragmento nem inversão de ordem. O problema novo está no parser tolerante: o decoder estrito de JSON rejeita quebras de linha literais dentro das strings, e o caminho de recuperação de "array truncado" entrega só o trecho anterior à primeira quebra.

Watch for: (1) uma resposta `["Oi", "Horários:\n• 10h\n• 11h"]` emitida com quebras de linha reais dentro da string vira apenas `["Oi"]` e o cliente nunca recebe a lista de horários, enquanto o checkpoint guarda a resposta inteira (confirmed, reproduzido executando `parse_reply_messages`); (2) após o teto de espera, um cliente que digita continuamente ainda pode manter o agente cancelando e reiniciando a cada mensagem (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

A reserva de posição resolve ordem e cancelamento com áudio sem risco de conversa travada: `fill`/`release` sempre agendam um ciclo novo, e os timeouts de download, transcrição e aviso de falha (30s/45s/30s) limitam o tempo de uma posição pendente.

O teto de espera limita só a fase de sleep: depois dele, cada mensagem cancela o ciclo em execução e o novo roda sem janela de debounce.

A recuperação de arrays malformados do parser usa o decoder estrito e perde conteúdo quando as strings têm quebras de linha literais. O rollback com `AsyncPostgresSaver` segue sem validação por falta de ambiente; está registrado como pendência de staging e não bloqueia.

<summary>Issues (4)</summary>

1. **Quebra de linha literal em string JSON descarta conteúdo (blocking, confirmed)** — usar `json.JSONDecoder(strict=False)` em `_find_json_array` e `_extract_complete_strings`, e cobrir com teste uma resposta com `\n` real dentro de uma string.
2. **Array com itens não-string ainda envia JSON cru (low, confirmed)** — `["Oi", 1]` ou `["Oi", {"a": 1}]` cai em `format_for_whatsapp(raw_text)`; extrair só os itens string ou usar o fallback.
3. **Residual de starvation depois do teto de espera (low, possible)** — com `delay == 0` cada mensagem cancela o ciclo e dispara nova chamada ao LLM; considerar manter um mínimo de janela ou tornar o ciclo não interrompível após o teto.
4. **`fill`/`release` depois do `shutdown` agendam ciclos órfãos (low, possible)** — `shutdown()` limpa `_states`, mas uma posição ainda pendente chama `_schedule` ao ser preenchida; marcar o debouncer como encerrado e ignorar novos agendamentos.

## Parser: quebra de linha literal em string JSON

`_find_json_array` e `_extract_complete_strings` usam `json.JSONDecoder()` com `strict=True`, que rejeita caracteres de controle (inclusive `\n` real) dentro de strings. Como a saída começa com `["`, `parse_reply_messages` classifica o resultado como array truncado e recupera apenas as strings completas anteriores à primeira string com quebra de linha:

```
parse_reply_messages('["Oi", "Horários:\n• 10h\n• 11h"]', 5)  ->  ['Oi']
```

O mesmo texto com `strict=False` é decodificado inteiro. Em v1 esse caso enviava o JSON cru; agora envia uma resposta incompleta sem aviso (só um `WARNING` de "truncated/malformed"). O prompt manda usar `\\n`, mas respostas com lista de horários são exatamente onde modelos costumam emitir quebras reais, e a parte perdida é a pergunta ou a lista que o cliente precisa para continuar. Se nenhuma string for recuperável, o cliente recebe o fallback "Desculpe, não consegui processar", mesmo que um agendamento já tenha sido criado pela tool no mesmo ciclo. A correção é de uma linha por decoder e os testes existentes só cobrem `\\n` escapado.

Também em `parse_reply_messages`: um array válido com item não-string (`["Oi", 1]`) segue o ramo "sem array de strings" e envia o texto bruto com colchetes e aspas (confirmed, executado). É o resquício do problema 6 da v1, mais raro que o caso anterior.

## Teto de espera e ciclo em execução

`_wait_delay` retorna `min(debounce, oldest_arrival + max_wait - now)` sobre o fragmento mais antigo do buffer, que só é consumido quando um ciclo termina. Passado o teto (4x o debounce), o delay vira 0: o ciclo começa na hora, mas qualquer mensagem seguinte o cancela, faz rollback e inicia outro também sem janela. Um cliente que manda mensagens em intervalos menores que a latência do LLM nunca recebe resposta e cada mensagem gera uma chamada ao LLM descartada. A limitação está documentada na docstring; o custo adicional é uma chamada ao LLM descartada por mensagem em rajadas longas (possible, requer tráfego sustentado acima de ~40s).

## Shutdown e posições pendentes

`shutdown()` cancela os ciclos e chama `self._states.clear()`. Um webhook que ainda esteja transcrevendo áudio mantém a referência ao `_ConversationState` antigo; ao terminar, `fill`/`release` chamam `_schedule` e criam uma task nova fora do dicionário, depois de o checkpointer ter sido fechado pelo lifespan. O ciclo falharia ao acessar o checkpoint e seria logado (possible: janela estreita, só no desligamento).

## Cobertura de testes

Not tested: string JSON com quebra de linha literal; array com itens não-string; `fill`/`release` depois de `shutdown()`; comportamento após o teto de espera com mensagens contínuas durante a execução do ciclo; `AsyncPostgresSaver` (pendência de staging aceita).
